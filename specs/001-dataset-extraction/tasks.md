# Tasks: Extração, Validação e Persistência do Dataset Experimental

**Input**: Design documents from `/specs/001-dataset-extraction/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md); Constitution v1.2.1 (`.specify/memory/constitution.md`)

**Tests**: INCLUÍDOS. A Constitution (Princípio VI) exige suíte própria para o motor, a validação, a persistência e a integridade, e o plano lista os testes obrigatórios. Em cada história, os testes vêm antes da implementação: escreva-os e confirme que **falham** antes de implementar.

**Organization**: tarefas agrupadas por história de usuário (US1 a US5, na ordem da spec) para implementação e teste independentes.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: pode rodar em paralelo (arquivos diferentes, sem dependência de tarefa incompleta)
- **[Story]**: história da spec (US1 a US5); só nas fases de história
- Caminhos relativos à raiz do repositório
- **Onde rodar**: nada de C++ de terceiros roda no host. Comandos usam `docker compose run --rm app ...` (com rede) ou `docker compose run --rm sandbox ...` (sem rede; obrigatório para o que compila ou executa C++ e para o `pytest`)

## Regras que valem para TODAS as tarefas (Constitution, Princípio XI)

- **📌 PROPAGAR**: uma tarefa marcada com 📌 produz dado medido ou decisão nova. Ela **só está concluída** depois de a informação ser escrita, **na própria tarefa**, em `docs/metodologia-referencia.md` (seção certa + nova linha datada na seção 8) **e** nos artefatos da feature que ela afeta (`spec.md`, `plan.md`, `research.md`), com data e fonte (ferramenta, revisão do dataset). Não existe tarefa separada de "atualizar a metodologia depois".
- **Documentação como critério de aceite (verificável)**: cada tarefa de README de módulo segue [`docs/template-modulo.md`](../../docs/template-modulo.md) (seis campos) e só termina quando `docker compose run --rm app python scripts/check_docs_sync.py --module src/<modulo>` sai com `0` (checagens C1 a C3). Todo comando documentado nasce `pendente` na tabela "Comandos verificados" do README e só passa a "verificado" (data, revisão git, tarefa) na tarefa que o executa de verdade; um módulo com `Status: implementado` não pode ter linha `pendente`. Toda tarefa que altere o `README.md` da raiz também reescreve a frase "Estado atual" e a data (checagem C4). O README do módulo é atualizado na história que entrega o comando, não no fim. **Revisão do carimbo**: saída de `git rev-parse --short=7 HEAD` **no host**, obtida depois de commitar o código e antes de rodar o comando; com sufixo `+dirty` se `src/`, `scripts/`, `pyproject.toml`, `uv.lock`, `Dockerfile` ou os arquivos do compose tiverem alterações não commitadas (alterações só de documentação não contam). O contêiner não tem `.git`, então o script confere apenas o formato; o fechamento (`--closing`) rejeita `+dirty`.
- **Restrições de schema** citadas literalmente de [data-model.md](./data-model.md) fazem parte do aceite; não as reinterprete.
- Nenhum limite de tempo/memória de problema é constante no código (Constitution, Princípio V); todo aleatório usa `random.Random(f"{SEED}:{contexto}")` com `SEED = 42`.

## Path Conventions

Projeto único em `src/<modulo>/` e `tests/<modulo>/` (espelhando `src/`); dois pacotes nesta feature: `src/sandbox/` (motor compartilhado, D7) e `src/dataset/`. Fundação do repositório: `pyproject.toml`, `uv.lock`, `Dockerfile`, `docker-compose.yml`, `README.md`, `docs/`, `manifests/`, `scripts/`.

## Implementation Strategy

### MVP First (US1 + US2, as duas P1)

1. Fase 1 (Setup) e Fase 2 (Foundational)
2. US1 (pool elegível classificado) e US2 (motor verificado, começando pelo gate T037) em paralelo
3. **PARE e valide**: `pytest` de US1/US2, `selfcheck` com código `0`, pool real documentado (T035) e motor confirmado (T049)
4. Somente então US3

O valor científico completo (100 WAs por problema, AC validado) só existe ao fim da US3; US1 e US2 sozinhas já entregam o pool e o motor confiável, e reduzem o risco de descobrir problemas tarde.

### Incremental Delivery

1. Setup + Foundational → ambiente pronto
2. US1 + US2 → MVP (pool + motor)
3. US3 → piloto de 10 problemas (**gate do risco 1**) → execução completa de 200
4. US4 → retomada comprovada
5. US5 → dataset empacotado e verificável, pronto para os módulos seguintes
6. Polish → conformidade e fechamento

### Gate de viabilidade (T071)

A fração de incorretas que é WA real só o motor mede. Se o piloto indicar que 200 problemas com exatamente 100 WAs não fecham, a execução completa NÃO segue: os autores decidem (nunca há relaxamento automático, FR-017).
